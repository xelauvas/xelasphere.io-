# MemPalace Integration — Plan Deltas

> **Purpose.** When implementation discovers the plan got something slightly wrong — an import path, a library API that changed, a test fixture that needs an extra arg, an ordering constraint the plan missed — the fix goes in the code *and* gets one line here. Future-you reading the plan in month 8 wonders why the code diverges; this file explains.
>
> The plan at `2026-04-20-mempalace-integration.md` is the frozen record of what we decided on 2026-04-20. The deltas here are the ground truth as of execution time.

## Format

**One dated entry per discovery.** Don't collect a day's findings into a single aggregate entry (the 2026-04-20 M0.3 library-isolation entry below is aggregated only because every sub-point shares one root cause and the lineage matters). The month-8 reader searching for "when did we first hit issue X" needs a timeline of discoveries, not a narrative. Each entry is self-contained: sub-milestone, what the plan said, what the code actually does, why, and the commit SHA.

- `YYYY-MM-DD M0.x` — [one-line change]. Commit `<sha>`. Reason: [why].

## Deferred to M0.11 (metrics + /readyz dispatch)

Items surfaced in earlier-milestone reviews that are correct to defer but easy to forget when M0.11 gets scoped as "just add the Prometheus metrics." Read this list at M0.11 dispatch time and expand the scope if anything is still outstanding.

- **Concurrent cold-palace open benchmark** (from M0.3.1-5 sign-off 2026-04-20). `PalaceRegistry._construct_entry` runs inside `_registry_lock`, serialising all cold opens at ~50-200ms each. Add `test_benchmark_concurrent_cold_opens` that fires N simultaneous first-touch opens, measures p95 queueing delay, and documents the threshold at which the sentinel-pattern fix is warranted. Gates the fix on measured evidence, not premature optimisation.
- **Full structured-logging middleware** (from M0.4 quality review 2026-04-20). Spec §8.4 prescribes `ts, service, level, event, user_id, turn_id, route, latency_ms, err, request_id`. Ingest route currently hashes `user_id` inline via `_hash_uid`, but `latency_ms`, `route`, and `request_id` are still missing. M0.11 lifts the hash helper into a shared `logging_utils` module and adds a per-request middleware that captures the missing fields.
- **`mempalace_ingest_total{status=error}` label** (from M0.4 quality review 2026-04-20). Spec §8.1 lists `status={accepted,duplicate,error}` as the intended labels. Ingest route currently only emits `accepted` / `duplicate` (via `AddDrawerResult.status`); `error` requires the route to catch + classify library exceptions and emit a metric with the `error` label before re-raising. M0.11 adds the wrapper.
- **`mempalace_delete_total` multiproc wiring** (from M0.8 quality review I1, 2026-04-21). `mempalace_sidecar/routes/lifecycle.py` declares the counter on `prometheus_client`'s default registry. Under multi-worker uvicorn (spec §5.8 sets `PROMETHEUS_MULTIPROC_DIR`), default-registry counters produce non-monotonic scrapes across workers: each worker has its own value, and Prometheus sees whichever worker answered the `/metrics` request. M0.11b's metrics-module consolidation must route all counters through `prometheus_client.multiprocess.MultiProcessCollector` so cross-worker aggregation works. Interim mitigation: the systemd unit should set `--workers 1` explicitly until M0.11b lands. Applies to any counter M0.9-M0.11a adds — all of them should land under the shared multiproc wiring from day one once M0.11b establishes it.

- **Spec §4.2 latency-anchor amendment** (from M0.5 latency investigation 2026-04-20, deltas entry C). The current §4.2 numbers (hot p95 ≤150ms, hard cap 500ms) were engineering aesthetics chosen in advance of measurement. M0.5's singleton fix landed wake-up p95 around 100ms on a 300-drawer palace on AMD EPYC-Rome. M0.11 should rewrite §4.2's targets as `measured-baseline × 1.3` formulas anchored to the M0.11 benchmark run, with the raw measured number captured in a dated benchmark file. Hardcoded ms numbers rot; ratios against measured baselines age more gracefully.

## Deferred architectural considerations

Notes about future architecture decisions that are not blocking M0.x but would be expensive to discover late. Each note has a concrete trigger condition so it stays actionable instead of decaying into folklore.

- **Wake-up on critical path vs. pre-fetch** (flagged 2026-04-20, deltas entry B). Current architecture places wake-up on the critical path of every turn. At ~100ms p95 on 300-drawer palaces, this sits comfortably under the 150ms target. As palaces grow, the fixed per-embed cost (~85ms with the singleton + intra_op=1 patch) stays roughly constant but retrieval-graph traversal grows sub-linearly; the comfortable margin will compress. Pre-fetch patterns — wake-up on WebSocket open and cache for N seconds, or wake-up parallel with LLM system-prompt ingestion — move wake-up off the critical path and insulate against this growth. Not a blocker at current scale. **Review trigger: hot p95 crosses 100ms on any production palace.** At that point, the critical-path architecture decision needs to be made before it becomes a visible latency regression.

- `2026-04-21 M0.10 shutdown protocol — THIRD consecutive plan-sketch bug caught by teeth-bearing test (doctrine promoted)` — **Headline finding from M0.10 Stage 3 GREEN.** `shutdown_sequence` phase-1 gate sketched `if not request.app.state.accepting:` in the middleware's `dispatch`. `starlette.requests.Request.app` is a property that does `self.scope["app"]` and raises `KeyError` when ASGI scope lacks the `"app"` entry — which happens only in minimal unit-test scopes (integration flow always has Starlette populate `scope["app"]`). `test_middleware_counter_sequence_under_exception` (unit, from Stage 1 RED) caught it on first Stage-3 run: `KeyError: 'app'` during the exception-path sequence assertion. Fix: `request.scope.get("app")` defensive lookup with `scope_app is None` treated as "accepting" (matches the test-harness intent: no app → no gate). Commit `b7e912a` (shipped with GREEN). In a real-app integration test this bug would NEVER have bitten because `scope["app"]` is always populated; only the unit-isolation test with its deliberately-minimal scope exercised the failure mode.

    **Pattern completed — three consecutive milestones, three structurally orthogonal bug classes.** M0.8 was library-semantic (chromadb close-before-pop since 1.5.x). M0.9 was filesystem-semantic (Linux `write_text` truncates shared inode through hardlinks). M0.10 is runtime-semantic (Starlette `Request.app` raises KeyError under minimal scope). All three: plan code compiles, plan code is correct against the nominal context, plan code breaks in the specific context the test exercises. This rules out "narrow domain luck" — the mechanism generalises across interface categories.

    **Sharper heuristic (replaces the M0.9 formulation).** The plan-sketch isn't wrong about what the interface DOES. It's wrong about what the interface does in the specific CONTEXT the code will actually run in. `.close()` under a subsequent same-path reopen. `.write_text()` on a file with `st_nlink > 1`. `request.app` on a scope without an `"app"` key. Doctrine rule: **when writing a teeth-bearing test for any filesystem/library/runtime interface, exercise it under the nastiest reachable context, not the nominal one.** "Reachable" = a context the production code path or a unit-test harness will actually produce. "Nastiest" = the one most likely to violate an assumption the sketch didn't name.

    **Operational promotion: doctrine moves from named principle to B4 checklist item.** The earlier M0.8+M0.9 formulation was "write teeth-bearing tests" — easy to forget to actually exercise the nasty context when fatigued. B4 now requires each test-plan entry to name the nasty context it exercises, not just the assertion depth. See template dispatch-template.md B4 edit in the same commit. Lower variance — the discipline survives a bad day.

- `2026-04-21 M0.10 shutdown protocol Stage 3 GREEN headline` — Spec §5.7 six-phase shutdown landed: `shutdown_gate` (flip `app.state.accepting=False`) → `shutdown_worker_cancel` (cancel KG worker with 10s `wait_for`) → `shutdown_drain` (block on `InFlightCounter.wait_idle(drain_timeout_sec)`) → `shutdown_registry_close` (`registry.close_all()` wrapped try/except so phase 5 still fires on failure) → `shutdown_systemd_notify` (emit `STOPPING=1`) → `shutdown_done`. `InFlightCounter` is coroutine-safe (not thread-safe) — asyncio.Event-based idle signal wakes drain the instant the last handler's try/finally decrement fires, not via polling. Middleware uses `try/finally` around `call_next` so the counter decrement runs on both success and exception paths. Phase-1 gate returns 503 `{"detail": "shutting down"}` for new non-exempt requests without bumping the counter. Idempotency guard via `app.state._shutdown_done` set BEFORE any phase runs — integration tests invoke `shutdown_sequence` explicitly inside a `lifespan_context`, and the lifespan's own finally block calls it again; the guard makes the second call a no-op. Lifespan's pre-M0.10 ad-hoc cancel/wait/close/notify trio deleted; replaced with `await shutdown_sequence(app, drain_timeout_sec=settings.drain_timeout_sec)`. Seven teeth-bearing tests gate the surface (2 unit + 5 integration); the 6-phase log-marker integration test doubles as operator-journal-debugging contract. Ladder: 98 → 105. Commit `b7e912a`.

- `2026-04-21 M0.9 runner meta.json write-through-hardlink bug — SECOND consecutive plan-sketch bug caught by teeth-bearing test` — **Headline finding from M0.9 Stage 3 GREEN.** Plan code at line 2784 shipped `(migrating / "meta.json").write_text(json.dumps({...}))` directly on a hardlinked meta.json. Linux does NOT copy-on-write hardlinked files — `write_text` uses `open(..., 'w')` which truncates the shared inode, propagating the new `schema_version` through every hardlink including primary's meta.json (which becomes `.replaced_<ts>/meta.json` after the first rename). Result: `.replaced_<ts>` shows `target_version` instead of the pre-migration version, defeating rollback integrity at the single file the runner itself writes. Surfaced by `test_atomic_rename_happy_path` asserting `.replaced_<ts>/meta.json` has `schema_version == 0`; failed with `assert 1 == 0`. Fix applied in commit `271d51c` (M0.9 GREEN): `if meta_path.stat().st_nlink > 1: meta_path.unlink(); write_text(...)`. The `unlink()` removes only the migrating-side hardlink; primary's copy survives with `st_nlink` decremented. Effectively copy-on-write for the runner's own write.

  **Pattern observation — second consecutive milestone, plan-sketch bug caught by teeth-bearing test.** M0.8 found chromadb close-before-pop was silently incorrect since M0.3 (plan assumed GC-sufficient close; chromadb 1.5.x requires explicit close). M0.9 found runner meta.json write was corrupting the snapshot (plan assumed `write_text` was COW; Linux filesystem semantics disagree). Both caught by teeth-bearing tests specifically exercising the failure mode. Neither caught by reviewers (spec or quality) — they caught the observable symptoms on code, but the UNDERLYING filesystem/library assumption bugs only surface when the test exercises the actual failure mode.

  **Template-level reflection (for next revision pass).** The plan sketches are design intent, not safety-verified artifacts. Two layers of verification now well-established:
    - Pre-resolution catches *plan-vs-reality drift*: spec wording that conflicts with current code, stale method names, deprecated patterns. Named in template Part 1.
    - Teeth-bearing tests catch *plan-vs-correctness drift*: plan code that looks right but has latent filesystem/library semantic bugs. Named in template Part 2 B4 (absence-vs-presence principle).
  Both necessary. Neither subsumes the other. Expect more such findings at M0.10+ as milestones accumulate filesystem/library interaction surface. Not failures — the discipline working.

  **Known v1 limitation surfaced during the investigation.** Post-migration writes to primary (chromadb ingest, turns.sqlite inserts, kg.sqlite triple adds) propagate through hardlinks to `.replaced_<ts>` during the 24h retention window. The runner's own meta.json write is now safely guarded (this commit), but chromadb/turns/kg writes inside the library/sidecar code are NOT — they happen via normal app flow after migration completes. Implication: `.replaced_<ts>` is only a valid rollback target immediately after migration (before any primary-side write). Subsequent operations gradually corrupt the snapshot via hardlinks. The 24h retention is a disaster-window *visibility* mechanism, not a guaranteed rollback. A future enhancement (M1?) could add a post-migration "seal" step that iterates primary/ and breaks all hardlinks (copy-over pattern) — expensive for large palaces (~100MB copy per migration) but preserves true 24h rollback integrity. Flagged to reviewers at M0.9 review pair dispatch; they weigh whether v1 acceptance of this limitation is OK.

- `2026-04-21 M0.8 chromadb close-before-pop drift discovery` — **HEADLINE FINDING: M0.3.x-M0.7 close paths were silently incorrect for chromadb 1.5.x.** Surfaced during M0.8 Stage 3 GREEN when `test_delete_then_reopen_creates_fresh_palace` failed with `chromadb.errors.InternalError: ... (code: 1032) attempt to write a readonly database`. Error code 1032 is SQLITE_READONLY_DBMOVED ("database file has been moved since the connection was opened"). A fresh `PersistentClient` opened for the same path after an rmtree inherits stale rust-side sqlite lock state from a predecessor client that was popped-from-`_clients` but never explicitly `.close()`d. Diagnosis: chromadb's documented lifecycle in 1.5.8 requires `client.close()` on the popped client, not just dict removal + GC. The library's own docstring for `PersistentClient.close()`: *"This is particularly important for PersistentClient to avoid SQLite file locking issues."* Spec §5.3 Close-order language was written against chromadb 0.6.x-era behavior where dict-pop + GC was sufficient; the contract drifted in 1.5.x and we didn't notice because no earlier milestone exercised close-then-reopen on the same path within a process lifetime — LRU eviction is rare in integration tests (test palaces are small, idle TTL is 4h, nothing triggers size-pressure under test load), idle-sweep fires on 4h timers that tests don't wait for, and shutdown close_all runs at test teardown when nothing reopens. Every existing `handle.close()` caller was technically incorrect since M0.3, the symptom was latent, and the M0.8 teeth-bearing DELETE-then-reopen test was the first to exercise the pattern and expose the bug. Fix: `mempalace_sidecar/palace_handle.py` `close()` now calls `client.close()` after popping from `_DEFAULT_BACKEND._clients`, guarded by try/except for forward-compatibility. Commit `b300206`. Spec §5.3 amended (this date). Upstream issue to be filed against `MemPalace/mempalace`. **Template-level lesson for future teeth-bearing tests:** "absence of bad state" assertions (like the pre-existing `test_registry_eviction_bounds_backend_cache`'s `palace_path not in _clients`) are weaker than "presence of good state" assertions. Popping-a-dict-key tests the absence; opening-a-new-client-and-successfully-writing tests the presence. The latter catches drift; the former doesn't. `test_registry_eviction_bounds_backend_cache` has been augmented with a presence assertion (same commit) so future regressions of the close path fail red, not silently latent.

- `2026-04-20 M0.5 finding B — chromadb DefaultEmbeddingFunction re-instantiation per call` — **10× wake-up speedup from an 8-line fix.** Commit `a8c7ed7`.

  **Finding.** chromadb 1.5.8 at `chromadb/api/types.py:965`:

  ```python

      from chromadb.utils.embedding_functions.onnx_mini_lm_l6_v2 import (
          ONNXMiniLM_L6_V2,
      )
      return ONNXMiniLM_L6_V2()(input)
  ```

  `DefaultEmbeddingFunction.__call__` constructs a fresh `ONNXMiniLM_L6_V2` on **every** call, triggering cold lazy-init of the tokenizer (~5ms) and ONNX `InferenceSession` (~180ms) per embedding.   **Independent second cause.** With the singleton in place at chromadb's default `intra_op_num_threads=0` ("use all cores"), four concurrent embeddings each tried to fan out across all 16 cores, producing severe context-switch contention — 4-concurrent p95 climbed to 1291ms, a ratio of 4.36× vs single-call p95 (296ms). Setting `intra_op_num_threads=1` + `inter_op_num_threads=1` made each embedding single-threaded so N concurrent embeddings parallelize across N separate cores with near-flat p95.

  **Empirical impact** (300-drawer palace, AMD EPYC-Rome VPS):

  ```
                          pre-patch  post-patch (singleton + intra_op=1)
  semantic_search p95:    412ms      95ms        (4.3× faster)
  build_wakeup p95:       768ms      106ms       (7.2× faster)
  4-concurrent ratio:     4.36×      1.35×       (3.2× better scaling)
  ingest per-drawer:      299ms      104ms       (2.9× faster)
  ```

  **Fix site.** Monkey-patch `DefaultEmbeddingFunction.__call__` in `mempalace_sidecar/_chromadb_patch.py`, imported from the top of `mempalace_sidecar/__init__.py` so the patch lands before any chromadb collection is constructed. The patched call routes through a process-global single-threaded `ONNXMiniLM_L6_V2` subclass. Safety: `InferenceSession.run()` is thread-safe per ONNX runtime docs; Rust-backed tokenizer is thread-safe. Vector stability: same class, same default pad=256, deterministic — byte-identical embeddings for identical input pre- and post-patch, no palace rebuild required.

  **Defensive guards.** Version pin (`assert chromadb.__version__ == "1.5.8"`) fails loud on upgrade; idempotency guard via `_xela_patched` marker prevents double-patch; three canary tests (`test_patch_applied_on_bare_import`, `test_default_ef_singleton_invariant`, `test_patch_idempotent`) catch both regression of our patch and upstream fixes.
