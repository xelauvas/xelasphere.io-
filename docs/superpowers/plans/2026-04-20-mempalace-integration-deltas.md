# MemPalace Integration — Plan Deltas

> **Purpose.** When implementation discovers the plan got something slightly wrong — an import path, a library API that changed, a test fixture that needs an extra arg, an ordering constraint the plan missed — the fix goes in the code *and* gets one line here. Future-you reading the plan in month 8 wonders why the code diverges; this file explains.
>
> The plan at `2026-04-20-mempalace-integration.md` is the frozen record of what we decided on 2026-04-20. The deltas here are the ground truth as of execution time.

---

## Format

**One dated entry per discovery.** Don't collect a day's findings into a single aggregate entry (the 2026-04-20 M0.3 library-isolation entry below is aggregated only because every sub-point shares one root cause and the lineage matters). The month-8 reader searching for "when did we first hit issue X" needs a timeline of discoveries, not a narrative. Each entry is self-contained: sub-milestone, what the plan said, what the code actually does, why, and the commit SHA.

- `YYYY-MM-DD M0.x` — [one-line change]. Commit `<sha>`. Reason: [why].

- `2026-04-20 review response` — Seven findings from the consistency-pass review of the PalaceHandle design-pass commit `528d197` applied:
  - **#1 idempotency authority.** Spec §4.1 now names `turns.sqlite` as the single authoritative dedup; the `Idempotency-Key` HTTP header is advisory (correlation only). Eliminates the silent-disagreement failure mode between header-driven dedup and library-derived-drawer-ID dedup.
  - **#2 library-ID-derivation survival test.** New test in M0.3.0 (`test_turns_authoritative_when_library_id_derivation_changes`): monkey-patches `miner.add_drawer` to produce a different drawer_id for the same `turn_id` and asserts `turns.sqlite` still blocks the duplicate. Empirical proof that our dedup survives an upstream hash-scheme change.
  - **#3 SCHEMA_VERSION bump.** M0.4.2 plan now explicitly instructs bumping `SCHEMA_VERSION = 1` → `2` when the first new route (`/ingest`) lands, honoring spec §5.2's "schema change without bump = PR failure" discipline. OpenAPI snapshot that enforces this ships in M0.12; until then, bump is documentation discipline.
  - **#4 parallelism enforcement test.** New test in M0.5.3 (`test_wakeup_concurrent_faster_than_sum_of_parts`): asserts `total < 0.7 * (l0 + 2*l3)` serial-bound so a subagent that implements M0.5.2 without `asyncio.to_thread` fails red instead of silently running serially.
  - **#5 metric rename.** Plan and spec: `mempalace_embedding_seconds` (which assumed a standalone Embedder) → `mempalace_chroma_query_seconds` with `layer={l2,l3}` labels, measuring Chroma's internal embed+search cost together (which is what our p95 budget is actually defined against).
  - **#6 embedding-model process-scope statement.** Spec §5.3 now explicitly states the model is process-global (sentence-transformers caches by name in module-level state); cold palace opens do NOT re-load the model. New test `test_cold_palace_open_reuses_embedding_model` asserts this.
  - **#7 two-phase eviction.** Plan and spec §5.4 rewritten: Phase 1 (inside `_registry_lock`) selects candidates and removes from cache; Phase 2 (after lock release) acquires each evicted user's write lock, then calls `handle.close()`. Closes the concurrency hole where a reader mid-call with `self._collection` in its stack frame could race with `_clients.pop` under single-phase eviction. New test `test_eviction_drains_readers` asserts the fix.
- `2026-04-20 M0.3 library isolation` — **Major reconciliation.** Plan's M0.3-M0.8 assumed `from mempalace import Palace` with a `Palace.open(path)` OOP handle exposing `.knowledge_graph`, `.close()`, `.add_drawer()`, `.recent_drawers()`, `.session_drawers()`, `.topic_search()`, `.semantic_search()`, `.search()`, `.list_drawers()`. That class does not exist in `mempalace==3.3.1`. The installed library ships a functional-module API: path-threaded helpers in `mempalace.palace`, `mempalace.miner`, `mempalace.searcher`, `mempalace.layers`, plus `KnowledgeGraph(db_path=...)` as a real OOP class. Introduced **PalaceHandle** as the sidecar-owned OOP wrapper at spec §5.3 — the library-isolation boundary. Plan M0.3 gets a new sub-task M0.3.0 that builds PalaceHandle; M0.3.1-M0.3.5 (registry) consume it; M0.4-M0.8 route implementations call `handle.foo(...)` bridged to the path-threaded primitives. Upgrading or replacing mempalace is now a PalaceHandle-only concern, not a cross-cutting rewrite. This note alone is worth the delay: in month 14 it turns "why is there this weird wrapper layer" into "oh right, the library isolation boundary."
  - **Ruled out:** option A (use a newer mempalace / fork with OOP Palace) — PyPI has 3.3.1 as latest, no metadata suggesting a 4.x OOP rewrite, homepage at `github.com/MemPalace/mempalace`. Dead unless a WIP fork surfaces later.
  - **Spec never specified `Palace.open()`.** Grepped the design doc; zero hits for `Palace.open`, zero for `mempalace==`. The OOP class shape was a plan-only invention — "pure reasoning-by-analogy."
  - **mcp_server NOT used.** Library ships 29 tool handlers via `TOOLS` + `handle_request`, but every handler calls `_get_collection(create=False)` against a module-level `_config: MempalaceConfig` and `_collection_cache`. Every `tool_*` operates on a single global palace bound at process start — a cross-user data leak in a multi-tenant sidecar. Spec §5.3 codifies "don't bridge to mcp_server"; a unit test greps the sidecar package and fails if `mempalace.mcp_server` appears as an import.
  - **`_DEFAULT_BACKEND._clients` cache-eviction contract.** The library's `ChromaBackend` singleton keeps an unbounded `{palace_path → PersistentClient}` dict with no public eviction API. Spec §5.3 states the contract with teeth: every `PalaceHandle.close()` MUST `pop()` that entry; `_evict_to_fit_unlocked` and `sweep_idle` MUST call `handle.close()` on every evicted entry; three teeth-bearing tests (`test_close_pops_backend_cache`, `test_registry_eviction_bounds_backend_cache`, `test_delete_pops_backend_cache`) fail if a future refactor silently reintroduces the leak. Upstream issue to file: [upstream issue not yet filed — target: before P0 entry] requesting `mempalace.palace.close_backend(palace_path)` as a proper public API.
  - **`turn_id` encoded in `source_file`.** `miner.add_drawer` generates drawer IDs as `sha256(source_file + str(chunk_index))[:24]` and discards arbitrary metadata. Encoding our `turn_id` into `source_file=f"turn:{turn_id}"` with `chunk_index=0` produces deterministic per-turn IDs — equivalent idempotency via a different mechanism. Pinned `mempalace==3.3.1` exactly (not `>=`) because the encoding trick rides on the library's hash derivation, which could change silently in a future release.
  - **`ingest_log.sqlite` collapsed into `turns.sqlite`.** Plan's original M0.4.2 had a separate `IngestLog` module with its own sqlite table keyed on `turn_id`. PalaceHandle's `turns.sqlite` already owns this schema (PRIMARY KEY turn_id + session + pair indexes) for the same purpose; two tables would be strictly worse. Route now delegates idempotency to `handle.add_drawer`.
  - **`cursor` → `offset` pagination.** ChromaDB `col.get` has no cursor concept — `limit`/`offset` is the only pagination primitive. Spec §5.2 and plan M0.6.2 updated. Route returns `{drawers, total, next_offset}`.
  - **Embedding is Chroma-internal.** Plan's M0.5 pre-embedded the query once and passed the vector to L2/L3. Reality: `mempalace.searcher.search_memories` takes a `query: str` and embeds internally via ChromaDB's default embedding function. No shared-embedding optimization is available without reaching past `search_memories` to `col.query(query_embeddings=[vec])` — a measurement-gated future optimization, not a design commitment. M0.5.1 simplified from an `Embedder` class to a `prime_embedding_function(warmup_palace_path)` that forces ChromaDB to resolve and load its model at startup.
  - **`asyncio.gather` does NOT parallelize sync layer calls.** All four `handle.*` layer methods are synchronous Python bodies. Plan's original `asyncio.gather(l0(), l1(), l2(), l3())` ran them sequentially on the event loop. M0.5.2 now wraps each in `asyncio.to_thread(...)` for real parallelism, with spec §5.3 explicitly stating that the serial-vs-concurrent choice is measurement-gated: if M0.5.3 measurement shows serial is within §4.2's latency budget, a follow-up commit may swap back.
  - **Three orthogonal version dimensions.** Spec §5.6 now documents Chroma on-disk format (library-managed by `mempalace.migrate.migrate`), drawer `normalize_version` (library-managed by `file_already_mined` auto-rebuild), and our `meta.json schema_version` (our M0.9). Conflating them in month 14 was a real risk; the table saves hours.
  - **Naming collision, semantically distinct.** `mempalace.layers.MemoryStack.wake_up()` returns a pre-composed string of L0+L1 only and is synchronous. Our wake-up is a four-layer structured-dict composition that reuses the library's Layer0-Layer3 classes as retrieval primitives (partially — L0 in the library is identity text, not recent drawers, so we reimplement). Spec §5.3 names the collision explicitly.
  - **PalaceHandle v1 scope.** Covers only M0.3-M0.8's surface — no `tunnel_follow`, `diary_*`, or `convo_*` methods. v2 extends when M0.17+ reaches those features. Holding scope deliberately.
- `2026-04-20 M0.2` — Quality-review fixes applied beyond plan:

  - `auth.py`: `EXEMPT_PREFIXES` renamed to `EXEMPT_PATHS`; match is now `path == p or path.startswith(p + "/")` so that a rogue route at `/healthzetc` or `/metricsX` cannot bypass auth by prefix accident.
  - `main.py`: bare `except Exception: pass` in sd_notify helpers narrowed to `except ImportError` (systemd-python missing) and `except OSError` (NOTIFY_SOCKET missing or dead); common body factored to a private `_sd_notify(message)`. Prevents silent swallowing of programmer errors (e.g. a future API shape change in `systemd.daemon`).
  - `config.py`: `data_dir` validator renamed `_must_exist` → `_must_be_writable` and raises `ValueError` if the directory exists but isn't writable by the process. Catches the systemd misowner failure mode explicitly instead of letting the first write crash.
